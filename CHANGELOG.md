## [Unreleased]

### Fixed
- **The "Sign in to Pratala services" prompt is now recoverable for email-SSO accounts.** The prompt's button only ran the NEP-413 wallet challenge, which SSO accounts cannot sign by design — so when the boot-time session confirm failed once (it raced an API restart during the move to the developer's local Postgres, and its error was only `console.warn`'d), the inbox/supplier prompt offered a button that could never succeed for that user. The mutation now calls the Auth0 verify-sso binding for SSO accounts (`ssoDerivedPublicKey` + `verifySsoSession`) and keeps the NEP-413 path for wallets; a successful boot re-confirm also invalidates `me` so the prompt clears immediately instead of waiting out the stale window. Diagnosis verified the backend healthy end-to-end first (minted session → `/auth/me`, profile write through the API, `SponsoredAccount` rows intact) — a frontend recovery gap, not data loss.
- **SSO harvest registration no longer fails ("Invalid NEAR Auth token", then "Pratala API is unavailable")** — four relayer bugs, all surfacing on the per-action MPC popup path's first live run (open item 2). (1) The backend pre-verified *every* NEAR Auth JWT against the tenant's API audience (`https://api.testnet.fast-auth.com`), but the per-action MPC signing JWT the SDK embeds in each confirmation window (`verify_payload`, with `fatxn`) is minted with the tenant's *signing* audience (`auth0.jwt.fast-auth.testnet`) — so login (API-audience token) worked while any relayed signing action (register_lot, funding, faucet) always failed the `aud` check. `relaySignTx` now verifies against the signing audience (mapped from the configured Auth0 domain, same table as the SDK's `FAST_AUTH_AUTH0_DEFAULTS`; unknown domain fails boot); identity endpoints keep the API audience. (2) The relayed `sign` call omitted `algorithm`, which the fast-auth contract's deserializer requires (panic: `missing field algorithm`) because the schema made it optional and the web app never sends it — it now defaults to `eddsa`, matching the SDK's `createSignAction`, and the sponsor signer requires the field so it cannot be dropped again. The real `jwtVerify` failure reason is also logged at `warn` (it was `debug`, invisible) so the next token problem is diagnosable from default logs. (3) The signature extractor read only the relay outcome's top-level `SuccessValue`, but `FastAuth.sign` is a promise chain (guard verify → MPC sign → callback) whose eddsa response (`{scheme, signature}`) surfaces in a *receipt* outcome while the top level is `null` — crashing with "Cannot read properties of null (reading 'signature')". The web signer now scans the top-level status and every receipt outcome for an MPC response and reports receipt failures/logs when none is found, and the API logs each relayed sign tx hash. (4) The relayed `sign` call attached no deposit, but the contract guards it with `assert_one_yocto` (panic: "Attached deposit is lower than required. Attached: 0, required: 1") — the sponsor now attaches exactly 1 yoctoNEAR, refunded with the signature. (`24771ca`, `722817c`, `1e18301`, `bbbf160`)
- **NEAR AI evidence check is live end-to-end** (no code change): the account was topped up with $1 credit, clearing the `no_limit_configured` blocker. A real `POST /api/ai/check` through a signed-in browser session returned 200 with verdict, findings, `provider_tee` signature and a cloud.near.ai verify URL (the test photo — a lake — was correctly failed as "not a farm field" at 0.95 confidence). First live exercise of the whole chain: upload → GCS read → TEE vision model → signed receipt → AiCheck row.
- **Email-SSO signing no longer lies "You cancelled the approval" or double-prompts**: every confirmation-window failure (popup blocked by the browser, window timeout) was classified as a user rejection, so a blocked window showed "You cancelled the approval. Nothing changed." — and declining the one-time quick-signing-key window immediately chained a second surprise window for the action itself. Popup-blocked/timeout failures are now a distinct `WindowBlockedError` with copy telling the user to allow popups (`tx.windowBlocked`, in the toast and the inline status line), and a declined or blocked key-bootstrap stops the action cleanly — one predictable confirmation per click, after which the action signs silently in the same click (docs/WALLETS.md §1 updated).
- **Intents checkout tab no longer fails with a bare "Internal server error"**: 1Click runs on mainnet only and answers testnet recipients — every account in this demo — with a generic 400 of exactly that text, which the API passed through verbatim, so the "Other chains" estimate could never complete. `POST /intents/quote` now rejects `*.testnet`/`*.betanet` recipients up front with an actionable message, and rewraps 1Click's generic rejection bodies into a hint that carries the provider `correlationId`. The checkout tab gains an explicit "Recipient on NEAR (mainnet)" field, prefilled with the signed-in account and flagged inline when it is a testnet id, so the dry estimate completes for any mainnet name (INTERFACES §5.1 documents the rule). Live-verified: 360 USDC (Base) → 359.96 USDC on NEAR.
- **iPhone HEIC photos no longer upload as HEIC**: the evidence uploader now detects HEIC by magic bytes, converts it to JPEG in the browser (`heic2any`, loaded only when needed) and re-embeds the photo's GPS + capture-time EXIF into the JPEG (`piexifjs`) before hashing and uploading. Before, Chrome/Firefox showed a blank preview (only Safari decodes HEIC) and the stored evidence + AI check received HEIC bytes. Conversion failure is a hard error on the photo, never a silent HEIC upload. Verified in-browser: HEIC in → JPEG stored (`image/jpeg`, hash matches the UI fingerprint), preview decodes.
- 5xx API responses no longer swallow the server's message: `ApiUnavailableError` keeps the body's `message` (e.g. the NEAR AI upstream error), and the verify AiPanel shows it after "AI check unavailable" instead of hiding the cause.
- E2E env no longer inherits the developer's `backend/.env` (Vitest loads it): the sponsor wallet vars are pinned empty so the 503 `sponsor_unconfigured` paths test for real.
- NEAR Auth identity tokens now use (and accept) the tenant's default API audience (`https://api.testnet.fast-auth.com`): the shared testnet client refuses to issue signing-audience tokens without a transaction payload, which made the first email login fail with `access_denied`. The signing audience stays internal to the per-action MPC flow. (`903f6ab` follow-up)
- GCS boot check writes and deletes a probe object instead of reading bucket metadata — `roles/storage.objectAdmin` keys lack `storage.buckets.get` and the old check would have crashed boot with the least-privilege key.
- `GCS_KEY_FILE` accepts a path relative to `backend/` (the key lives at `../config/…json`); it resolves identically from the dev source tree and the compiled `dist/` build.
- Wallet modal ("Meteor Web" button) was unclickable: our connect sheet stayed open as a modal behind NEAR Connect's popup. The sheet now closes before handing off; all dialogs keep `.hot-connector-popup` clickable and don't treat it as an outside click (`290cce3`).
- `scripts/02-create-accounts.sh` aborted on near-cli-rs 0.31's new key-scheme prompt; now passes `--signature-scheme ed25519` (`6dd4bae`).
